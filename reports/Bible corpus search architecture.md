# Build OpenLogos search on one embedded core

OpenLogos does not need a search server, a vector database, or a graph database to deliver Logos- and Accordance-class search. Every biblical corpus is tiny by information-retrieval standards: the SBLGNT has **137,740 word tokens** and MACULA's segmented Hebrew Bible has **475,910 rows** ([macula-greek](https://github.com/Clear-Bible/macula-greek/tree/main/SBLGNT/tsv); [macula-hebrew](https://github.com/Clear-Bible/macula-hebrew)). So the winning design is one Rust core that runs identically on iOS, Android, macOS, WASM and the Obsidian plugin, built from five parts. **SQLite** is the canonical store, using the official sqlite-wasm `opfs-sahpool` build in browsers. **FTS5 with a shared Rust Greek/Hebrew normalizing tokenizer** handles keyword, phrase and Boolean search. A **custom columnar token table with roaring-bitmap postings** handles lemma, morphology, proximity, syntax and alignment queries. **sqlite-vec** stores quantized, precomputed vectors and runs brute-force search on them. **Typed edge tables queried with recursive CTEs** handle cross-references, citations, lexeme relations and translation lineage. The optional self-hosted tier should be **Postgres + pgvector** running the same Rust core, not OpenSearch, Elasticsearch or Neo4j. Those engines add operational weight and, in several cases, copyleft or source-available licenses, and they solve scale problems this corpus does not have. The hard parts are elsewhere: the data, meaning token-keyed alignments, versification mapping and license-clean datasets; the embedding quality on Koine Greek and Biblical Hebrew, which no public benchmark measures; and an AI workflow in which models propose, deterministic tools verify and humans promote. The open questions are concrete benchmarks rather than architectural unknowns, and they are listed at the end.

## Twelve query primitives cover what scholars and preachers actually run

Commercial and academic tools look different on the surface, but they all compose the same few primitives. Logos separates Morph Search (lemma, part of speech, case, tense, mood over tagged Greek NT, Hebrew Bible and LXX), Syntax Search and Clause Search ([Logos](https://faithlife.com/logos-syntax-search)). Its morph syntax combines lemma predicates, morph codes and positional operators in one expression, for example `lemma:διά@P BEFORE 1 WORD @NG` for a preposition followed immediately by a genitive noun ([Logos forum](https://community.logos.com/discussion/121385)). Clause Search finds terms "acting in specific grammatical or semantic roles", such as Jesus as subject and Peter as object, but it works only on texts that have syntax analysis. One user reported that only SBLGNT, LXX Swete and LBH were searchable there ([Logos forum](https://community.logos.com/discussion/comment/1238195)). Users also query by Louw-Nida semantic domain when clause search cannot express what they want ([Logos forum](https://community.logos.com/discussion/comment/1238204)). Accordance's graphical Construct window links word items with **WITHIN n words** and **AGREE** connectors, the latter requiring matching lemma or case across columns ([Accordance help](https://accordancefiles1.com/helpfiles/OSX13/content/topics/11_ggtt/the_agree_connecting_item.htm)). Users report false and missed hits from AGREE even with "search both directions" on, which shows that agreement queries need a careful engine and good UI feedback ([Accordance forum](https://forums.accordancebible.com/topic/7781-want-to-find-noun-preposition-same-now/)).

The academic tools expose the same primitives as text languages. Text-Fabric templates nest units by indentation (chapter → sentence → word). They support feature conditions (`pos=verb|noun`, regex `lex~^walk`, numeric comparisons), slot relations (overlap, embedding, adjacency, within-k), cross-node feature agreement via `.f.`, typed edge traversal (`-sub>`, `<crossref>95>`), and quantifiers (`/without/`, `/where/…/have/`) evaluated as separate searches combined by set algebra ([Text-Fabric search](https://annotation.github.io/text-fabric/tf/about/searchusage.html)). ANNIS AQL addresses nodes as `#1`, `#2` and links them by overlap, adjacency and dominance operators, some with edge labels ([ANNIS AQL](https://korpling.github.io/ANNIS/4/user-guide/aql/index.html)). MACULA supplies the layers that make these queries possible on open data: syntax trees, semantic roles, participant referents, word senses, English glosses and morphology ([macula-greek](https://github.com/Clear-Bible/macula-greek)).

The table maps each query type to the data it needs and to the index that answers it. That mapping is the specification for the OpenLogos query engine.

| Query type | Example | Data required | Index technique |
|---|---|---|---|
| Lemma / Strong's occurrence | every ἀγαπάω | token table, lemma column | lemma → roaring bitmap of token ids |
| Morphology filter | aorist imperatives of X | per-field morph columns | bitmap per (field, value), intersected |
| Proximity / sequence | X BEFORE/WITHIN 3 words Y | global token positions | shift-and-intersect or merge-join |
| Within unit | same verse, clause, sentence | span tables per level | parent-id column per level |
| Agreement | noun–prep–noun, same case | columns compared across tuple members | filter during join |
| Syntax / clause role | Jesus subject, Peter object | tree + role edges | parent array + pre/post-order intervals |
| Semantic domain | Louw-Nida / SDBG domain 25 | multi-valued domain column | domain → bitmap, prefix ranges |
| Referent | all mentions of Peter incl. pronouns | referent column | entity → bitmap |
| Rendering per translation | English words for each ἀγάπη | token-keyed alignment | forward and reverse alignment maps |
| Faceted counts | hits by book × rendering | hit list + columns | group-by over compact columns |
| KWIC concordance | context windows | surface + trailing punctuation | positional slice |
| Cross-refs, quotations, parallels | OT in NT, Synoptics | verse-range edges with type, weight | adjacency keyed by verse |

The driving example, "every ἀγάπη/ἀγαπάω versus φιλέω with English renderings", turns out to be simple once broken down. It needs three lemma posting lists, a join against a per-translation alignment table, and a group-by over translation × rendering × book. No syntax engine is involved, and the lists are small: **ἀγαπάω 143, ἀγάπη 116, φιλέω 25** tokens in SBLGNT ([macula-greek TSV, computed](https://github.com/Clear-Bible/macula-greek/tree/main/SBLGNT/tsv)). Any reasonable layout answers it in milliseconds. The real constraint is the alignment, and it must be keyed to tokens rather than Strong's numbers. Strong's-keyed links such as STEPBible's TTESV are easy to build but cannot distinguish two ἀγαπάω tokens in the same verse ([STEPBible-Data](https://github.com/STEPBible/STEPBible-Data)). MACULA's `xml:id` (for example `n40001001001`, book-chapter-verse-word) and OSHB's immutable word ids ([morphhb](https://github.com/openscriptures/morphhb)) are the natural token keys. Strong's-level views should be derived from token alignments, never the reverse.

Relations come in two kinds that the data model must keep apart. Curated relations have a named source: TSK and OpenBible cross-references, OT quotations, parallel passages, lemma and domain links, citations extracted from commentaries. Model-derived similarity is the second kind. Preachers and teachers lean heavily on the first: cross-references, "who cites this verse", word studies by lemma and rendering, and parallels. Scholars add morphology, syntax and agreement queries on top. Semantic "passages about hospitality" search is a recall aid for both groups, not a replacement for either.

## Sub-million-token corpora favor a custom bitmap index over any search server

### SQLite and FTS5 are the only store that is first-class everywhere

SQLite is the only relational engine that runs natively on every OpenLogos target, including browsers. The official sqlite-wasm build offers two OPFS VFSes. `opfs` needs COOP/COEP headers. `opfs-sahpool` needs no special headers, has the best performance, and has worked on all major browsers since March 2023, at the cost of limited multi-connection support ([SQLite WASM persistence](https://sqlite.org/wasm/doc/trunk/persistence.md)). That trade-off suits OpenLogos well. The Obsidian plugin runs in an Electron renderer where header control is limited, and a single Rust core in one worker needs only one connection. The same docs warn that OPFS locks files exclusively, even for reads, and that a pause/unpause locking bug existed before 3.54, so the WASM build should pin SQLite at 3.54 or later.

FTS5 covers keyword, phrase, prefix, NEAR and AND/OR/NOT queries, and it accepts custom tokenizers through the `fts5_tokenizer` API alongside built-in `unicode61` (with diacritic removal), `porter` and `trigram` ([SQLite FTS5](https://www.sqlite.org/fts5.html)). OpenLogos should register one Rust tokenizer. For Greek it strips accents and breathings and folds final sigma. For Hebrew it strips niqqud and cantillation (U+0591–U+05C7). The same function normalizes queries, so normalization logic exists once and behaves identically on every platform. The search key is a derived field. Display text stays byte-exact as received, because Unicode canonical ordering of Hebrew points conflicts with typographic order and NFC normalization reorders meteg, dagesh and vowels ([ConTeXt list](https://mailman.ntg.nl/archives/list/ntg-context@ntg.nl/thread/X4OC7XCYR4TSW3J53JD6FCRNZ7KMYXJR); [Meteg](https://en.wikipedia.com/wiki/Meteg)).

### The linguistic engine should copy Text-Fabric's model, not Lucene's

The documented academic tools all use custom, in-memory, column-oriented designs rather than general-purpose search engines. Text-Fabric numbers word slots 1..maxSlot and places phrases, clauses, verses and books as higher nodes linked to slots through `oslots`. Features are integer→value maps, edges are (int, int)→value maps, and plain `.tf` files compile to binary caches on first load ([Text-Fabric data model](https://annotation.github.io/text-fabric/tf/about/datamodel.html)). Corpus Workbench applies the same idea to flat token streams with "multiple layers of word-level annotation" ([Evert & Hardie 2011](https://eprints.lancs.ac.uk/id/eprint/62721/)). Text-Fabric's model is also the cleanest open reference because its "warp" (otype, oslots, otext) is separate from "weft" features, so third-party annotation modules layer onto a fixed base. OpenLogos needs that property for user and community annotation packs.

The recommended Rust engine has seven parts:
- a dense token table with dictionary-encoded columns (surface, normalized form, lemma id, each morph field, domain, referent, syntactic parent);
- per-(feature, value) **roaring bitmaps** over global token positions;
- per-level parent-id columns for "within verse/clause/sentence";
- a parent array with pre/post-order intervals for dominance tests;
- CSR-encoded edge tables for alignment, referents and cross-references;
- a join engine for sequence, proximity and AGREE;
- a Text-Fabric-style set-algebra layer for quantifiers.

roaring-rs is pure Rust, Apache-2.0 and actively released (v0.11.5, August 2026), so the same code compiles to iOS, Android, desktop and wasm32. Its C sibling CRoaring adds NEON and AVX-512 SIMD if profiling ever demands it ([roaring-rs](https://github.com/RoaringBitmap/roaring-rs); [CRoaring](https://github.com/RoaringBitmap/CRoaring)). The bitmaps serialize into SQLite BLOBs, so no second storage engine is needed. At roughly 138k Greek tokens even a brute-force column scan is sub-10 ms work, so indexes matter mainly for interactive faceting across many translations and for multi-node syntax queries. That figure is an estimate from corpus size, not a measurement.

### Tantivy, OpenSearch and Elasticsearch lose on portability, not quality

Tantivy is healthy (MIT, 0.26.1, May 2026) and an excellent Lucene-style library natively ([Tantivy](https://github.com/quickwit-oss/tantivy)), but official WASM support is still an open RFC ([issue #541](https://github.com/quickwit-oss/tantivy/issues/541)). The browser builds that exist are community efforts with immutable segments that cannot accept additions after finalization ([test-tantivy](https://github.com/StyMaar/test-tantivy)), and a release build in an old demo was about 1.5 MB ([tantivy-wasm](https://github.com/phiresky/tantivy-wasm)). Making it the cross-platform FTS engine would tie the web and Obsidian paths to unofficial builds. It also would not help with morphology. Lucene-style engines index documents rather than token-feature lattices, so lemma-plus-case-plus-proximity queries would mean reimplementing the linguistic engine in an engine-specific DSL. The same objection applies more strongly to OpenSearch (Apache-2.0, healthy under the Linux Foundation) and Elasticsearch (triple-licensed AGPLv3/SSPL/ELv2 since August 2024) ([OpenSearch](https://github.com/opensearch-project/OpenSearch); [BusinessWire](https://www.businesswire.com/news/home/20240829537786/en)). Both are JVM clusters built for workloads several orders of magnitude larger, they cannot run offline on a phone, and they would force query logic to live in two places. Meilisearch (MIT CE plus BUSL-1.1 EE since v1.19) and Typesense (GPL-3.0) are easier to operate but similarly weak at linguistic queries ([Meilisearch EE](https://www.meilisearch.com/blog/enterprise-license); [Typesense](https://github.com/typesense/typesense)). The steelman for a server engine is multi-tenant full-text search over large user-generated corpora. If OpenLogos ever hosts thousands of users' private libraries, revisit then. That is not the launch problem.

Turso, the Rust rewrite of SQLite, is the most interesting future alternative. It is SQLite-file-compatible, has a WASM binding, Tantivy-backed FTS and MVCC. But it is pre-1.0 (v0.9.0-pre.1, October 2026), its README recommends independent backups, its FTS is experimental, its ANN index is "on the roadmap", and it lists no Swift or Kotlin bindings ([Turso README](https://github.com/tursodatabase/turso)). File compatibility makes a later migration cheap, so it belongs on the watch list rather than in the foundation.

## Vectors serve recall, anchored on translations rather than original languages

### No embedding model has been measured on Koine Greek or Biblical Hebrew

No public benchmark evaluates multilingual embedders on Ancient Greek or Biblical Hebrew retrieval. The SIGTYP 2024 organizers explicitly call for a universal benchmark for ancient-language embeddings ([SIGTYP 2024](https://aclanthology.org/2024.sigtyp-1.19.pdf)), and model cards list modern Greek ("el") and modern Hebrew ("he") rather than "grc" or "hbo". The best ancient-domain evidence points one way: small adapted encoders beat generic ones. A July 2026 study built a gold set of **2,935 expert-verified biblical parallels** in patristic Greek and Latin. It adapted a Greek/Latin token-level model into a sentence encoder with TSDAE and contrastive learning, and that encoder outperformed generic multilingual, distilled and supervised baselines, with gains peaking at only about 4–8k in-domain sentences ([arXiv 2607.24542](https://arxiv.org/abs/2607.24542)). Krahn et al. distilled multilingual sentence models into Ancient Greek BERTs using Greek–English parallel data and documented "translation bias": Greek vectors land near their English translations ([arXiv 2308.13116](https://arxiv.org/abs/2308.13116)).

The practical conclusion is to anchor semantic retrieval in the modern-language translations and let original-language passages inherit hits through verse and token alignment, which is exact and free. Original-language text should still get its own optional index, built from normalized surface or lemma sequences, for Greek-to-Greek allusion and reuse detection. Its quality has to be measured, not assumed. Lemma and Strong's ids stay exact-match filters, never vectors. Concept relations such as an LXX word reused in the NT should come from lemma data, with embeddings only nominating candidates.

EmbeddingGemma's Gemma license is not OSI-open and its weights are gated, so bundling it in an open-source app needs a license review. MIT/Apache e5 or Qwen3 models avoid that question. Model size is the binding constraint on devices. By parameter arithmetic, e5-small is about 120 MB at int8, EmbeddingGemma about 300 MB at int8, and Qwen3-0.6B or BGE-M3 about 600 MB at int8. That suggests two tiers kept in strictly separate vector spaces. Tier A is a small query model plus shipped corpus vectors for phones and the web. Tier B is a larger model and an optional reranker on Mac, iPad or the server. Whatever the tier, the corpus vectors and the query vectors must come from the identical model, revision, prefix strings and quantization. The vector-set manifest records each of those, and the core refuses to mix sets.

### One ONNX export, three runtimes

The portable inference path is a single ONNX export. The Rust core runs it through the `ort` crate on Apple platforms and Android. `ort` wraps ONNX Runtime 1.28, and CoreML or NNAPI execution providers may need custom-built binaries because prebuilt downloads cover only a few providers ([ort](https://docs.rs/crate/ort/latest); [ORT CoreML EP](https://onnxruntime.ai/docs/execution-providers/CoreML-ExecutionProvider.html)). The web runs the same weights in transformers.js on WebGPU, falling back to q8 WASM ([transformers.js v3](https://www.huggingface.co/blog/transformersjs-v3)). Candle is a plausible pure-Rust fallback that avoids ORT packaging, but the notes did not verify it. Apple's Foundation Models framework gives eligible devices a free, offline ~3B LLM for generation and grounding, but no embedding API from it was found ([createwithswift](https://createwithswift.com/exploring-the-foundation-models-framework/)). Retrieval must therefore never depend on it.

### Chunk by verse, retrieve by window, fuse with keyword search

Single verses ("And he said unto them…") match poorly in isolation, while pericopes match well but are hard to cite. The answer is parent-child retrieval. Embed each verse with a book/chapter/heading prefix, and embed 5-verse sliding windows (stride 2) or fixed pericopes. Score both, then resolve window hits to their best child verse. Take pericope boundaries from one fixed segmentation dataset rather than per-translation headings, so ids stay deterministic. Commentary chunks are paragraphs with a heading-path prefix and parsed `refs[]`, so they are retrievable by passage as well as by meaning. Lexicon chunks are one per sense, keyed by lemma. These chunking rules come from general RAG practice; no Bible-specific comparison was found.

Hybrid retrieval should be the default. On a modern-Greek benchmark of 104 expert queries, hybrid beat both BM25 (nDCG 0.544–0.652) and the best dense setup (up to 0.748) ([arXiv 2607.21274](https://arxiv.org/html/2607.21274v1)). Reciprocal rank fusion of FTS5 BM25 and sqlite-vec kNN needs no score calibration, which makes it ideal on device. BM25 over normalized lemma tokens matters more than dense retrieval for original-language text. A 0.6B cross-encoder reranking the top 20–50 is plausible on M-series hardware but borderline on phones; no on-device latency measurement was found, so it should be optional or server-side.

### Shipped vectors cost single-digit megabytes per translation

sqlite-vec returned in March 2026 ("sqlite-vec is back!") with stable v0.1.9 and ANN indexes (DiskANN, rescore, experimental IVF) only in alphas. Its v0.1.9 release ships Android builds and an unexplained `spm.json` asset ([sqlite-vec releases](https://github.com/asg017/sqlite-vec/releases)). Brute force is enough at OpenLogos scale. sqlite-vec supports `bit[]` binary vectors with an oversample-then-rescore pattern, and Matryoshka truncation via `vec_slice()` plus `vec_normalize()` ([binary-quant guide](https://https-alexgarcia_xyz.proxy.bugsmash.io/sqlite-vec/guides/binary-quant.html); [Matryoshka guide](https://https-alexgarcia_xyz.proxy.bugsmash.io/sqlite-vec/guides/matryoshka.html)). Secondary sources report binary embeddings keeping over 95% of retrieval accuracy at a 15–45× speedup ([ikyle.me](https://ikyle.me/blog/2025/binary-quantized-embeddings)). That claim is untested on biblical text. The arithmetic for one translation's 31,102 verses:

| Dims | float32 | int8 | binary |
|---|---|---|---|
| 256 (Matryoshka) | 31.8 MB | 8.0 MB | 1.0 MB |
| 384 | 47.8 MB | 11.9 MB | 1.5 MB |
| 768 | 95.5 MB | 23.9 MB | 3.0 MB |
| 1024 | 127.4 MB | 31.9 MB | 4.0 MB |

Windows add 30–50% more vectors. Commentaries dominate: 100k paragraphs at 768 dims is about 77 MB int8 or about 9.6 MB binary. The recommended package stores binary or 256-dim int8 vectors for the coarse scan and full-dim int8 vectors for rescoring, inside the same SQLite file as FTS5. Float32 never ships to devices. Embedding two or three representative translations per language and mapping by verse id covers most needs. If on-device collections grow into the hundreds of thousands of vectors before sqlite-vec's DiskANN stabilizes, USearch (Apache-2.0, v2.26.6, October 2026, with C, Swift and Java bindings) is the maintained embeddable ANN to add ([USearch](https://github.com/unum-cloud/usearch)). instant-distance is archived and sqlite-vss has been dormant since 2023, so avoid both ([instant-distance](https://github.com/instant-labs/instant-distance); [sqlite-vss](https://github.com/asg017/sqlite-vss)).

## Edge tables with recursive CTEs make a graph database unnecessary

OpenLogos's graph workloads are shallow and bounded: cross-references, citations, lexeme networks, syntax parent/child, translation genealogy. None of them needs a runtime graph algorithm. Practitioner write-ups converge on the same rule. Graph databases earn their place with unbounded-depth traversal or algorithm-centric workloads, while well-indexed edge tables with recursive CTEs handle 1–3 hop lookups ([Capital One](https://www.capitalone.com/software/blog/graph-database-evaluation/); [LatentView](https://www.latentview.com/blog/why-we-traded-a-graph-database-for-bigquery-ctes/)). One comparison measured a 6-hop indexed recursive CTE on a 200K-node graph at under 2 ms, and it identified the operational cost of a second database plus change-data sync as the larger burden ([Markaicode](https://markaicode.com/vs/neo4j-vs-postgres/)). That figure is a blog benchmark, not peer-reviewed. The data is small: OpenBible's cross-reference set is about **340,000 references** in a 2 MB zip ([OpenBible](https://www.openbible.info/labs/cross-references/)).

The embedded graph option also collapsed during the research window. Apple agreed to acquire Kùzu on 2025-10-09, and the repository was archived the next day ([BetaKit](https://betakit.com/apple-strikes-deal-to-acquire-canadian-database-software-startup-kuzu/); [kuzudb/kuzu](https://github.com/kuzudb/kuzu)). Its MIT fork LadybugDB is active (v0.22.0, October 2026) and offers Cypher, vectors, FTS, WASM and Swift bindings, but its governance is opaque and its iOS/Android packaging is unconfirmed ([LadybugDB](https://github.com/LadybugDB/ladybug)). CozoDB has not released since December 2023 ([cozo](https://github.com/cozodb/cozo)). On the server, Neo4j Community is GPLv3 and single-instance only ([neo4j](https://github.com/neo4j/neo4j)), and Memgraph Community is under BSL ([Memgraph](https://memgraph.com/blog/try-memgraph-enterprise-30-days)). Neither is warranted. If Cypher-style ergonomics are ever wanted, PostgreSQL 19 committed SQL/PGQ (`GRAPH_TABLE`, `CREATE PROPERTY GRAPH`) in March 2026, and it treats property graphs as views over ordinary tables ([depesz](https://www.depesz.com/?p=4467); [PG19 docs](https://www.postgresql.org/docs/19/sql-create-property-graph.html)).

The model is a single typed edge table, `edge(src_kind, src_id, rel, dst_kind, dst_id, weight, source_work, method, confidence)`, with covering indexes on (src, rel) and (dst, rel). Rows have three kinds of provenance. Curated rows carry a named source: TSK, OpenBible, a quotation list, a lexicon. Extracted rows carry a parser version. Model-derived rows carry a model version and a `similarity_score`, and they never get a curated `relation_type`. That separation lets the UI and the agents say "is semantically similar to" without ever implying "quotes". Centrality or "related passages" clustering is precomputed in the build pipeline and stored as edge weights. Translation genealogy (BSB → OpenLogos Normalized English, revision lineage, token `id_lineage`) uses the same table with `rel = derived_from | supersedes`.

## One SQLite-shaped core everywhere, Postgres only when users share data

### The layered architecture

Layer 0 is immutable **corpus packs**: one read-only SQLite file per edition or work. Each pack holds the verse/paragraph text, the FTS5 index, the token feature columns, the roaring bitmap BLOBs, alignment and edge tables, an optional sqlite-vec table, and a provenance manifest. Packs are content-addressed, signed, and `ATTACH`ed on demand. Layer 1 is a mutable **user database** (notes, highlights, tags, plans, accepted AI proposals) synced through an op-log or CRDT layer in the Rust core. The notes did not research sync libraries, so that choice remains open. Layer 2 is the **Rust query core**: normalization, query parsing, the token-feature engine, edge traversal, RRF fusion and the agent tool registry. Swift/TextKit 2, Kotlin, WASM and Obsidian call it through UniFFI or wasm-bindgen. Layer 3 is **optional on-device inference**: the ONNX query embedder and, where available, an on-device LLM. Layer 4 is the **optional self-hosted server**. It links the same Rust core and reads the same corpus packs with SQLite FTS5, which is possible because corpus text is read-only. Postgres + pgvector is added only for multi-user sync, shared annotations and large global vector sets. pgvector HNSW comfortably handles 1–5M vectors on one machine; that is an inference that still needs a benchmark. The server can also host query embedding and reranking for web clients that cannot download a 300 MB model.

| Server vector escalation | Qdrant | Apache-2.0 | Low ([qdrant](https://github.com/qdrant/qdrant)) |
| Build ETL | DuckDB 2.0 (not at runtime: vss persistence experimental) | MIT | Low ([vss docs](https://duckdb.org/docs/2.0/core_extensions/vss.html)) |
| Watch list | Turso 1.0, LadybugDB, Tantivy WASM, SQLite `vec1` | MIT / MIT / MIT / PD | Pre-1.0 or unverified |
| Avoid | Kuzu, CozoDB, sqlite-vss, instant-distance, sled, Jina v3 | — | Archived, dormant, or non-commercial |

### Size budget

The original-language token tables are a few MB each uncompressed, which is an estimate from row counts with about 25 dictionary-encoded columns. The raw MACULA Hebrew TSV is about 84 MB in Git LFS before encoding ([macula-hebrew](https://github.com/Clear-Bible/macula-hebrew)). Cross-references are about 2 MB compressed. Vectors for a translation are 1–8 MB at the recommended quantization, and a large commentary library adds about 10–80 MB. The largest single download is the query embedding model, at about 120–300 MB for the phone tier. That makes the model an explicit opt-in download with BM25-only fallback, and a reason for server-side query embedding on the web. The binary sizes of sqlite-wasm, sqlite-vec WASM and the Rust core WASM were not measured, and they are the first prototype measurement to make.

## A hash-pinned pipeline turns heterogeneous sources into signed corpus packs

### Ingestion normalizes every format into two intermediate models

USFM/USX/USJ is the living format family. **usfmtc** (MIT, 0.4.10, October 2026) is the USFM Technical Committee's reference implementation. It reads and writes all three formats and handles reference parsing and `.vrs` reversification ([usfmtc](https://pypi.org/project/usfmtc/)). **usfm-grammar** (MIT, 3.2.1, tree-sitter based) is a second credible parser ([usfm-grammar](https://pypi.org/project/usfm-grammar/)). The Rust crate **usfm3** (MIT, 0.2.0, error-tolerant, emits USJ/USX/USFM) fits a Rust build tool best but has a single maintainer ([usfm3](https://docs.rs/crate/usfm3/0.2.0)). The recommended setup is to normalize translations to USJ with usfm3 and run usfmtc in CI as a conformance oracle, diffing the USJ both produce for each book. Proskomma is labeled experimental and has no releases, so do not depend on it ([proskomma-core](https://github.com/Proskomma/proskomma-core)). OSIS (OSHB, SWORD modules) and TEI (MACULA, ThML-like works) are best handled by a streaming XML reader plus one small adapter per corpus. Each corpus uses its own subset, so a generic parser would not pay for itself.

Original-language sources become a token table. Each source keeps its native id as an immutable external key: OSHB `id`, MACULA `xml:id`, TAGNT/TAHOT ref plus index, BHSA slot plus version. OpenLogos mints an internal `edition:BBCCCVVVWWW[s]` id, where the morpheme suffix covers Hebrew prefixes, because OSHB splits prefixes with `/` inside one word while MACULA and BHSA split them into separate slots ([morphhb](https://github.com/openscriptures/morphhb)). A new upstream release triggers a token-level diff, which emits an `id_lineage` table (same/split/merge/insert/delete). Ids are never silently renumbered. BHSA's practice of storing immutable versions side by side is the model to follow ([ETCBC/bhsa](https://github.com/ETCBC/bhsa)).

### Licensing is a build gate, not an afterthought

The license-clean default stack is SBLGNT (CC BY 4.0 since December 2022) ([LogosBible/SBLGNT](https://github.com/LogosBible/SBLGNT)), WLC (public domain), OSHB lemmas and morphology (CC BY 4.0), MACULA Greek and Hebrew (CC BY 4.0 for Clear's trees, roles and referents) ([macula-greek LICENSE](https://raw.githubusercontent.com/Clear-Bible/macula-greek/main/LICENSE.md)), STEPBible data (CC BY 4.0, with an obligation to record and share changes) ([STEPBible-Data](https://github.com/STEPBible/STEPBible-Data)), Clear alignments (CC BY 4.0) ([Alignments](https://github.com/Clear-Bible/Alignments)), OpenBible cross-references (CC BY), and the BSB as the public-domain English base ([berean.bible](https://berean.bible/terms.htm)). MorphGNT's README still says the SBLGNT text is under the old EULA, which is out of date relative to the upstream relicensing.

Three traps need per-package rights flags. First, MACULA's Louw-Nida `ln`/`domain` columns are UBS MARBLE data "used with permission" with no open license. The CC BY-SA 4.0 UBS semantic dictionaries (SDBG/SDBH) are the open substitute and belong in a separate share-alike module ([UBS open access](https://translation.bible/open-access-resources/)). Second, ETCBC BHSA is CC BY-NC 4.0, so it can only be an optional user-downloaded module. Third, MorphGNT (CC BY-SA 3.0) imposes share-alike on derived morphology, which makes MACULA's CC BY morphology the more permissive choice ([morphgnt](https://github.com/morphgnt/sblgnt)). The packager fails any redistributable bundle that mixes NC, EULA or unflagged share-alike content.

### Versification pivots through the original-language scheme

There are three complementary versification resources. Paratext `.vrs` files define the schemes (org, eng, lxx, vul and others). The Copenhagen Alliance JSON format, now at nida-institute/versification, adds machine-readable mappings and **sniffing rules** that detect a text's scheme ([Copenhagen Alliance](https://github.com/Copenhagen-Alliance/versification-specification)). STEPBible's TVTMS is the most detailed scholarly table, covering splits, merges, partial verses and LXX sub-verses with rules such as "if this chapter has 29 verses, it is using Greek versification" ([STEPBible-Data](https://github.com/STEPBible/STEPBible-Data)). TVTMS uses NRSV as its English standard while Paratext and Copenhagen use `org`, so the two must not be mixed without an explicit crosswalk. A derived registry that treats KJV as the standard lists ranges, LXX sub-verses, merges and splits as out of scope, which shows exactly where the complexity lives ([bcv-commons](https://huggingface.co/datasets/bcv-commons/versification)). OpenLogos stores every text in its native scheme and compiles a `verse_map(scheme_from, ref_from, scheme_to, ref_to, kind)` table pivoting through `org`, so N schemes need N maps instead of N². Partial verses get sub-verse anchors, and Copenhagen sniffing at ingest acts as a QA gate on each text's declared scheme.

### Alignment becomes standoff records keyed by token

Inline alignment, such as unfoldingWord's `\zaln-s`/`\zaln-e` USFM milestones, suits editing but not querying, and even extracting plain text from it is "not perfectly straight-forward" ([Door43 forum](https://forum.door43.org/t/whitespace-in-unfoldingword-usfm-files/504)). Standoff alignment records keyed by token ids, the shape of Clear's proposed Scripture Burrito alignment flavor, which is still a "working proposal", suit an indexed package ([Alignments](https://github.com/Clear-Bible/Alignments)). Everything normalizes to `(source_token_ids[], target_token_ids[], status, origin, confidence, tokenization_hash)`. The hash invalidates an alignment automatically when either side is re-tokenized. Versification must agree before alignment. In one Door43 BSB alignment effort, verses whose numbering differed between UGNT and BSB were simply left unaligned ([Worldview_en_bsb](https://content.bibletranslationtools.org/DCS-Mirror/Worldview_en_bsb/commit/99f4f239c84ebc305e87f9dcc58fd8224ded7a2e)). Manual alignment of a Bible takes "about a decade of a scholar's time" per language ([SBL abstract](https://sbl-site.org/meetings/abstract.aspx?id=44231)). Translations without curated alignments therefore need a statistical aligner, run with a pinned seed and stored as `origin = auto:<tool>@<version>`. Eflomal and fast_align are the usual candidates, but the notes did not verify their licenses or maintenance.

### Commentaries enter through reference extraction

CCEL ThML often already carries parsed citations (`<scripRef passage="Rom. viii. 27,28" parsed="NIV|Romans|8|27|8|28">`), though `parsed` is optional and inconsistent in the wild ([CCEL ThML](https://www.ccel.org/ThML/scripref.htm)). Where it is missing, the openbibleinfo **Bible-Passage-Reference-Parser** (MIT, 4.0.0 July 2026, feature-complete, 50 bundled languages) produces OSIS refs with character offsets through `osis_and_indices()` ([bcv parser](https://github.com/openbibleinfo/Bible-Passage-Reference-Parser)). It has no Rust port, so it runs as a hermetic Node/Deno build stage. Each extracted citation becomes `(work_id, anchor, char_start, char_end, osis_ref, scheme, method, confidence)`, is mapped through `verse_map`, and lands in the edge table. That yields "who cites this verse" across the whole library and gives commentary chunks the `refs[]` that RAG retrieval needs.

### The DAG is small enough for a Rust runner

The stage DAG is fetch → parse → normalize → tokenize and mint ids → versify → align → enrich → index → embed → package. A `sources.toml` registry pins each upstream by commit or SHA-256 and records SPDX license, attribution, NC/SA flags, declared versification and normalization. Each stage's cache key is the hash of its code version, its config and its input hashes, which gives Nix-style incremental rebuilds. Sorted iteration, no wall-clock values, and fixed aligner seeds make outputs deterministic. Packages are deterministic archives, BLAKE3/SHA-256 addressed and signed, with an embedded provenance manifest whose attribution strings feed the app's credits screen. For a few dozen sources, a `cargo xtask` runner with hermetic Python subprocess stages (usfmtc oracle, Text-Fabric export) locked with `uv` beats Dagster or Airflow. That is an engineering judgment, not a sourced finding. QA gates check verse counts against `.vrs`, sniffing agreement, unique ids, resolvable alignment endpoints, token-count diffs between releases, morph-code validity, USFM round-trips and license compatibility. The **embed** stage uses the same pinned ONNX export the apps ship and runs the retrieval evaluation set before a vector pack is published.

## AI proposes, deterministic tools verify, humans promote

### Production translation pipelines all treat AI output as a draft layer

The most mature production system is SIL's. **Serval** (MIT) is a modular API with translation, word-alignment and corpus modules, and it implements NMT, SMT and statistical engines with GPU jobs queued through ClearML ([sillsdev/serval](https://github.com/sillsdev/serval)). Scripture Forge fine-tunes Meta's NLLB on a trusted "model text" plus the project's completed books, then drafts the next book. SIL states plainly that "rough drafts contain errors and require editing by skilled translators" ([SIL deck](https://docs.google.com/presentation/d/1t2R8e5dpjoign9IkKMaFI-T_Wk6NpYZ0/htmlpresent)). Drafts land in a separate "SF Drafts" project and are merged only after human editing, team checks and consultant checks. SIL's documented error profile is names, numbers, kinship terms, added or missing words, and inconsistent novel key terms, with strengths in naturalness and style consistency. Studies of general LLMs add theological drift: unguided ChatGPT, Copilot and DeepSeek tend to reproduce traditional conservative readings in contested passages ([Pistis & Praxis](https://periodicos.pucpr.br/pistispraxis/article/download/33897/28040/87653)). A 2026 study of LLMs in Bible translation concludes that human oversight is indispensable ([AUP Online](https://www.aup-online.com/content/journals/10.5117/KT2026.1.005.AMER)). Retrieval helps measurably. In low-resource MT, 50 BM25-retrieved examples match about 250 random many-shot examples ([arXiv 2604.02596](https://arxiv.org/html/2604.02596v2)), and a Dhao NMT+LLM refinement pipeline found that quality was driven mainly by the number of retrieved examples ([arXiv 2601.09982](https://arxiv.org/html/2601.09982v1)).

For OpenLogos's translation-research lab, this means several things. Inputs are limited to public-domain, CC BY and opted-in CC BY-SA texts. Copyrighted translations such as NET and LEB, whose terms govern quotation and distribution, appear only as user-licensed reference views and never as model inputs for a derived edition ([LEB license](https://lexhampress.com/LEB-License)). The base is the BSB, renamed per Berean's request that altered texts not use the Berean name. Drafting is conditioned on original-language lemmas, token alignments and a locked key-term glossary. Every model output is stored as an immutable `ai_proposal` with kind, target ref and token span, content, evidence, and full provenance: provider, model and version, prompt template id and rendered-prompt hash, steering profile, tool-transcript hash, source content hashes and input licenses. Proposals move through `proposed → auto_checks_passed|failed → under_review → accepted | accepted_with_edits | rejected | needs_consultant`. The automatic checks are deterministic. Numbers and names must match the aligned source tokens. Verse ids must exist in the edition's scheme. Key terms must render consistently per lemma unless a reviewer notes otherwise. Every content lemma must be aligned, and no unaligned target words may appear, which catches additions and harmonization. chrF++ and BLEU serve only as regression signals ([arXiv 2602.17425](https://arxiv.org/html/2602.17425v1)). The accepted translation is a derived edition, materialized from accepted proposals plus human edits, with every verse pointing back to its proposals and linked through `derived_from` edges.

### Agents call the same tools the UI calls

Community Bible MCP servers already exist, offering passage retrieval, FTS5 search, Strong's lookup, cross-references and unfoldingWord morphology ([Glama listing](https://glama.ai/mcp/servers/uu4vgy5cww); [GetBible MCP](https://glama.ai/mcp/servers/cy8kdomsy8)). That confirms the pattern but not their quality. OpenLogos should expose its own Rust core as an MCP server, or as an in-process tool registry when no MCP host is present, with tools such as `get_passage`, `lemma_search`, `get_alignments`, `get_cross_references`, `lexicon_entry`, `parallel_passages`, `semantic_search` and `verify_quote`. Each result carries edition id, scheme, OSIS ref, token ids and a content hash. Because the UI and the agents call the same deterministic functions, the app works fully without AI, and the AI layer stays provider-agnostic across subscriptions, BYOK and local models.

Grounding relies on the Anthropic Citations API where available. When the model cites supplied documents, the API returns `cited_text` with "guaranteed" valid pointers. Custom-content documents are used as-is, so one block per verse maps citation indices 1:1 to verse ids ([Claude Docs: Citations](https://platform.claude.com/docs/en/build-with-claude/citations)). Citations cannot be combined with structured outputs (the API returns a 400), so the flow has two steps: a cited prose answer, then a separate extraction into claim and evidence records. Local and OpenAI-compatible models lack the guarantee, so OpenLogos always runs its own post-hoc verifier. The verifier re-fetches each quoted span by ref, requires a normalized exact match, and flags or strips anything unverifiable. Semantic-search hits reach agents labeled as similarity with a model version, so an agent cannot present them as curated cross-references.

## Eight benchmarks decide what the research could not

The architecture is settled at the level of component characteristics, but no end-to-end measurement exists for this stack on Greek and Hebrew corpora. The questions below are ordered by how much each could change a decision.

| # | Open question | Benchmark to run | Decision it settles |
|---|---|---|---|
| 1 | Do generic embedders retrieve Koine/Hebrew acceptably after normalization? | Gold set of 100–300 graded topical queries, OT-in-NT quotation retrieval, Greek→English verse retrieval, commentary grounding via parsed refs, hard negatives; nDCG@10 and Recall@50 per language, modeled on [arXiv 2607.24542](https://arxiv.org/abs/2607.24542) and [2607.21274](https://arxiv.org/html/2607.21274v1) | Whether a fine-tuned ancient encoder (CSE on ~5k sentences) is needed |
| 2 | How much does binary/int8/256-dim quantization cost on biblical text? | Same gold set across fp32, int8, binary+rescore, 256/512/768 dims | Shipped vector format and pack size |
| 3 | What are the real WASM and mobile binary sizes? | Build sqlite-wasm + sqlite-vec + Rust core for wasm32 and both mobile targets | Web and Obsidian feasibility; lazy-loading strategy |
| 4 | Query-embed and rerank latency on mid-range phones | e5-small, EmbeddingGemma int8 and a 0.6B reranker via `ort` on iPhone and Android, plus transformers.js WebGPU/WASM | Tier A model choice; whether reranking is server-only |
| 5 | Is brute-force sqlite-vec fast enough at commentary scale? | KNN latency at 50k, 200k and 500k vectors on device | When to adopt sqlite-vec DiskANN or USearch |
| 6 | Linguistic engine latency for multi-node syntax and AGREE queries with facets across 10 translations | Port 50 representative Logos/Accordance/Text-Fabric queries; compare result counts against Text-Fabric on N1904 | Whether bitmap + parent columns suffice or a tree index is needed; correctness oracle |
| 7 | Can `opfs-sahpool` sustain the Obsidian plugin's access pattern? | Attach 10+ packs, concurrent UI and agent queries, SQLITE_BUSY handling | Web and Obsidian storage design |
| 8 | Statistical aligner accuracy versus Clear's manual alignments | eflomal/fast_align on BSB → MACULA, scored against Clear gold; license audit | Whether auto-alignment is trustworthy enough to show without review flags |

Several factual gaps also need closing before commitments are made: the purpose of sqlite-vec's `spm.json` and its iOS/WASM packaging; whether PostgreSQL 19 final has shipped; the Clear alignment file schema and which translations it covers; the exact UBS dictionary repository license; the WEB's modification and name terms; the licenses of eflomal, fast_align and SIL Machine; LXX dataset licensing, which was not researched at all; and the sync library for the user database (cr-sqlite, Automerge, Yrs or a custom op-log), which was out of scope.

## Conclusion

The research reverses the usual intuition about where Bible-software complexity lives. Storage and search engines are close to a solved, commodity problem at this scale, and choosing heavier infrastructure would cost OpenLogos its offline, single-codebase advantage without buying anything. The defensible moat lies in three data assets no off-the-shelf engine provides: token-keyed alignments between original-language tokens and openly licensed translations, a versification pivot precise to the partial verse, and a provenance model that keeps curated relations, model-derived similarity and AI proposals permanently distinguishable. Getting those right makes every query type, from a preacher's cross-reference lookup to a scholar's clause search, a cheap composition over the same columns.

The work should therefore be sequenced by uncertainty rather than by layer. The deterministic core (SQLite, FTS5, bitmap engine, edge tables) can be built now with low risk, and it is also everything the no-AI mode needs. The embedding and translation-lab layers should wait on the gold-set evaluation, because the single most consequential unknown in this report is whether any license-clean model represents Koine Greek and Biblical Hebrew well enough to trust. Until that is measured, translations should anchor semantic search, and original-language vectors should remain an optional, explicitly labeled experiment.
