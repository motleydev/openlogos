# ADR 0003 — Identity, anchors and schema versioning (v1 freeze)

Status: proposed by B006 on 28 October 2026 for the owner's review; the Rust types, JSON Schemas and conformance fixtures named below implement it. Builds on ADR 0001 (one Rust core, versioned bindings) and ADR 0002 (packs as SQLite files behind core traits).

## Context

Every durable thing a reader makes (a note, a highlight, a collection, an export to a vault) points at text through an anchor, and every pack carries tables (verse maps, token ids, lineage, alignments) that other packs and the user's data refer to. Once v1 ships, these identities and the files that carry them must stay readable: a note written on an iPad in year one must still find its verse after the edition is corrected, and a collection exported by version N must open in version N+1 without loss. specs/03-data-model.md and specs/19-search-and-retrieval.md state the intent; this ADR fixes the rules the code enforces.

## Decision

### Identity

1. **Token ids** are `edition:BBCCCVVVWWW[s]` (`core::anchor::TokenId`): edition id, USFM book number, chapter, verse and word as three digits each, and an optional lower-case morpheme suffix. `core::identity::mint_verse` fixes the minting rules: words are numbered from 1 in the edition's own reading order, counting orthographic words only; a word segmented into `n >= 2` morphemes gets suffixes `a`, `b`, … (at most 26); upstream ids (OSHB, MACULA) stay beside the minted id as external keys. Ids are minted once per (edition, content revision) and never renumbered.
2. **`id_lineage`** (`core::identity::IdLineage`) relates the ids of one content revision to the next with rows of kind `same` (1→1, same id), `split` (1→2+), `merge` (2+→1), `insert` (0→1+) and `delete` (1+→0). An id in no row is *unknown*, which is never read as deleted. A table from a revision to itself, a row of the wrong shape, a `same` row that renumbers, an id of another edition, or an id on the same side of two rows is rejected.
3. **Verse maps** (`core::versification::VerseMap`) store rows from each scheme to the Paratext/Copenhagen `org` pivot with kinds `equal`, `split`, `merge`, `partial` and `absent`; mapping pivots through `org`. A verse with no row is *unmapped*, never identity. `ReferenceMapping` (`VerseMap::map_many`) is the many-to-many record: source set, target set, status `exact` / `partial` / `ambiguous` / `unmapped`, the source verses an explicit `absent` row covers (omitted verses, additions seen from the other side) kept apart from the verses no row mentions, row provenance, path and notes. A `SegmentTable` says whether an edition prints a verse as its own segment, under a bridge label such as `3-4`, as several segments, or not at all.
4. **Alignments** (`core::identity::AlignmentSet`) are standoff records `(source_token_ids[], target_token_ids[], status, origin, confidence)` keyed to tokens, never to Strong's numbers, with status `aligned`, `partial`, `null` (exactly one side empty: explicitly no counterpart) or `disputed`, and origin `curated:<name>[@<version>]`, `auto:<tool>@<version>` or `user:<device>`. A token in no record is *unaligned*, which is different from `null`. The set carries the **tokenization hash** of each side: the lower-case hex SHA-256 of the UTF-8 lines `<token id>\t<surface>\n` for every token of the edition revision in id order. The pipeline computes it; the core compares it with what the pack declares (`package-manifest` 1.1 `edition_revisions[].tokenization_hash`) and refuses the set when either side differs.
5. **Anchors** (`core::anchor::Anchor`) hold edition, content revision, segment, a range in Unicode scalar values, the token ids under it and a W3C TextQuoteSelector when rights permit. UTF-16 and grapheme forms are adapters in `crates/text`, never stored. Reanchoring across a revision (`reanchor_across`) tries, in order: the same token ids in the new layout; the lineage's successors of those ids; the exact quote with its context; the exact quote alone. One hit is `exact` (same range and text) or `moved`; several are `ambiguous`; none is `orphaned`. A lineage that deletes every token of an anchor orphans it without trying the quote, so the same words elsewhere are never adopted. An orphaned anchor keeps its original target, in storage and in exports.
6. **Collections and receipts** (`crates/collections`) use stable ids matching `^[a-z0-9][a-z0-9-]{3,63}$` that are never derived from a title or a position. A source-bearing item keeps edition, artifact hash, content revision, locator, the original anchor and a snapshot of the quotation rights that applied; it stores quoted text only when that snapshot allows it. Observations and research excerpts are distinct kinds; machine output carries a generated label and never becomes a source quotation. A vault export receipt maps item ids to the block id `ol-<item id>`, a relative resource path, the last-export hash, the source revision and a disposition (`quoted`, `metadata_only`, `conflict`, `skipped`) with a reason for anything but `quoted`. Paths are not identity.

### Schema versioning

7. Every **top-level document** (pack manifest, study collection, vault export receipt, workspace, and the records to follow) carries `schema_version` as `MAJOR.MINOR` (`core::versioning::SchemaVersion`). **Pack tables** (verse map, lineage, alignment, anchor) carry none of their own: they are versioned by the manifest of the pack that holds them, which also records `core_api_version`.
8. A MINOR bump is additive: new fields are optional with a defined default, new enum values may be skipped by a reader that does not know them, and nothing is removed or re-interpreted. Anything else is a MAJOR bump, which is a new line with its own schema file and an explicit migration.
9. **Reading** (`SchemaVersion::compatibility`): a reader implementing `M.n` reads a file at `M.k` with `k < n` by filling the defaults of every field added since (`older_minor`); reads `M.k` with `k > n` by ignoring what it does not know and **never writing the file back** at its own version, because that would drop fields (`newer_minor`); refuses any other MAJOR (`older_major` unless a migration exists, `newer_major` with "update needed"). A JSON Schema file describes exactly one version and stays strict (`additionalProperties: false`); `tools/validate.py` keeps the previous MINOR's example under `examples/archive/` so the N reads N−1 rule is exercised on every run.
10. **Migrations** are pure functions from version to version over the JSON value, forward only, idempotent, and covered by a fixture per step. A migration never invents data: a field it cannot derive stays at its default and the record's own provenance (hashes, revisions, original anchors) is preserved. User data is migrated on read and written at the current version only after the user's device has the new version everywhere a sync could reach (specs/03, operation log); packs are never migrated in place, a new pack revision is built.
11. **`API_VERSION`** (`openlogos_core::API_VERSION`, now `0.1.1`) names the core API the UniFFI and wasm-bindgen surfaces are generated against. While MAJOR is 0, a breaking change bumps MINOR and an additive change bumps PATCH; from 1.0.0, MAJOR and MINOR respectively. A host built against `h` may load a core reporting `c` only when `api_compatible(c, h)`: same breaking line and at least as new. The pack manifest records the `core_api_version` its tables were written against, and a vault export receipt records the writer's; a core refuses a pack whose line it cannot read and says which version wrote it.

## Consequences

- Adding a field to a document is a MINOR bump plus a defaulted `#[serde(default)]` field in the Rust type, a schema edit, an archived example and a validator run. Renaming or re-typing a field is a new MAJOR line; the old schema file stays in `schemas/` until no supported reader writes it.
- `additionalProperties: false` in the schemas means a strict validator rejects a newer-MINOR file; readers in the core use serde's default of ignoring unknown fields, which is the `newer_minor` rule. The validator therefore validates files at their own declared version, never at the reader's.
- Deuterocanonical books, further schemes (`vul`, `lxx` variants) and new `LineageKind` or `AlignmentStatus` values are additive. Changing the token id format, the scalar-value offset unit or the `ol-` block id rule is a MAJOR change of the whole identity layer and is not planned.
- The hash algorithm for tokenization (item 4) is fixed here; the core does not compute hashes (no hashing dependency in the wasm build), so the pipeline (B063/B064) owns the computation and the conformance fixtures carry real values for the fixture token layers.

## Alternatives considered

| Option | Why not chosen |
|---|---|
| Serialize `TokenId` as its string form | Hosts already receive it as a record through UniFFI and serde-wasm-bindgen; changing the serialized form now is a breaking API change for no reader benefit. Fixtures use the string form and parse it. |
| One `schema_version` on every pack table | Tables inside one SQLite pack cannot drift from each other; versioning them through the manifest is one number to check instead of five. |
| Accept unknown fields in JSON Schema (`additionalProperties: true`) | Would hide typos and credential-shaped fields the validator exists to catch (specs/00-import-contract.md); strictness is kept and the version rule carried by the reader instead. |
| `Omitted` as a fifth mapping status | specs/03 fixes four statuses; omission is a property of the source verses (`absent`) and sits beside `unknown` in the record, which also keeps a single verse's status unchanged. |
