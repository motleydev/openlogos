### The round trip, as implemented on both surfaces

1. The surface shows a *display string*: verse numbers with a thin space, the verses joined by
   one joiner, paragraph breaks every eight verses in long sets, the attribution line. Only the
   verses and the joiner are *core text*; the rest are *non-core runs* (`RunMap`, and in the DOM
   the `.marker` elements).
2. A selection change gives a UTF-16 range in the display string. The surface widens a range
   that ends inside a grapheme cluster to the cluster (`rangeOfComposedCharacterSequences` on
   Apple, `Intl.Segmenter` on the web), then maps it to core text: an end inside a non-core run
   collapses to the run's edge, so a selection over a verse number alone is empty.
3. `selectionToAnchors(paragraph, utf16)` returns one anchor per segment with scalar ranges,
   token ids and the exact quote. `anchorToUtf16(anchor, segmentText)` gives each back as
   UTF-16; the segment's offset in the joined core text and the run map turn it into display
   ranges, which are painted (storage attributes on Apple, the CSS Custom Highlight API on the
   web). A verse number is never painted.
4. The verdict *identical* means three strings agree character for character: the anchors'
   quoted text, the text under the painted ranges, and the selected core text taken segment by
   segment (the joiner belongs to no segment).

error; a selection ending one unit inside "17 " stops at the edge and anchors "life." only; the

**What the surface does with a selection inside a grapheme cluster.** A user cannot make one:
both text views place carets and handles only on composed-character boundaries. Programmatically
the two platforms differ: `NSTextView.setSelectedRange` widens the range to the cluster itself
(kept {2, 3} for asked {3, 2}; {126, 4} for {128, 2}), while `UITextView.selectedRange` keeps the
mid-cluster range as given. The surface widens either way before calling the core, with the
platform's own composed-character sequences, and the readout says "widened to grapheme
clusters". The core was never asked for a mid-cluster range, so `NotGraphemeBoundary` did not
arise; the fixture's `snapped` ranges ({0,3} and {126,128}) are what came back.

**By hand.** The same cases were also made with the pointer on the Mac (drag across "life. 17
For God") and produced the same readout; the screenshots below are from the launch-argument
path so they are reproducible (`just b005-shot mac cross-verse 1440`).

**Real iPad.** None exists on this machine; the iPad half of the acceptance ran on the
simulator. The simulator uses the same UIKit and TextKit 2 code as the device, so the offset and
selection behaviour is the device's; the timings are not (section 6).

**macOS target.** `OpenLogosMac` built with no change to the B063 sources; the B005 code is

accessibility permission is needed, and the one AppleScript attempt that would have needed it

**OPFS and IndexedDB fallback — documentation, not measurement.** The core runs in a worker;
its packages and indexes need a durable file store. From the browsers' documented
capabilities (MDN and the vendors' release notes as of this spike), not measured here:

| Browser | OPFS (`navigator.storage.getDirectory`) | `FileSystemSyncAccessHandle` in a worker | IndexedDB | CSS Custom Highlight API | `Intl.Segmenter` |
|---|---|---|---|---|---|
| Chromium 86+ / 102+ | yes | yes (102+) | yes | yes (105+) | yes (87+) |
| Safari 15.2+ / 16.4+ | yes (15.2+) | yes (16.4+; sync handles are the SQLite-on-OPFS path) | yes | yes (17.2+) | yes (14.1+) |
| Firefox 111+ | yes (111+) | yes (111+) | yes | yes (140+) | yes (125+) |

`sqlite-wasm-rs` VFS the B064 engine already targets) when `getDirectory` and
`createSyncAccessHandle` exist; otherwise an IndexedDB-backed VFS (the same SQLite image stored
as pages in an object store, slower and without atomic multi-page writes, so writes go through
an operation log); private-browsing modes in Safari and Firefox may refuse or purge both, and
the reader must survive an empty store on next open (the specs/01 cold-open budget is measured
against OPFS only). Nothing here was exercised: the DOM reader keeps no state.

## 5. Acceptance 3: three panes plus notes dock — selection, focus, VoiceOver, scroll

Layout A, the B005 anchors scenario (three panes, the notes dock pinned), at 1024 × 768 and
1440 × 900 points.

### Scroll and selection latency

`-OPENLOGOS_PERF 1` makes pane 1 a synthetic 1,000-verse set (BSB John 3:16–17 repeated, 125
paragraphs of 8 verses, ids `John.c.v`), then a `CADisplayLink` scrolls the text view 12 points
per frame for 480 frames (wrapping to the top at the end; about 720 pt/s at 60 Hz) and records
the interval between frames, then makes 30 programmatic selections of about 40 units spread
through the document, one every six frames, timing the full `select(display:)` (text view
selection, scroll-to-visible, two core calls, paint) and the time to the next frame. The same
intervals are emitted as `os_signpost` intervals (`org.openlogos.app` / `reader`:
`scroll-measurement`, `selection-roundtrip`) for Instruments. Frames over 17.5 ms are missed
60 Hz frames; the simulator and the Mac mini's display run at 60 Hz.

Reading: scrolling the 1,000-verse set held 60 Hz on the simulator at both widths and on the
Mac at 1024; on the Mac at 1440 (a 1440 × 900 window, 359-point pane) 40 % of frames took two
display intervals, repeatably (the under-load run had 143 of 474). The programmatic scroll sets
the clip view's bounds origin and reflects it every frame, which redraws synchronously and
bypasses `NSScrollView`'s responsive-scrolling overdraw; a user's trackpad scroll takes the
other path, so this number says "profile it in Instruments" (the `scroll-measurement` signpost
is there), not "the Mac drops frames". Selection latency is 70–95 ms at p50 on all four,
of which the two core calls on the 1,000-segment paragraph are 25–28 ms at p50 (section 6) and
the rest is the text view's selection, scroll-to-visible of a range in a 125-paragraph
document, and the attribute paint; the first painted frame lands 100–117 ms after the request
at p50. For the two-verse panes of the anchors scenario the same pipeline measures 0.03–0.5 ms.

Method caveats: the simulator measures the Mac's CPU and GPU through a software-rendered iPad
screen, not an iPad; the Mac numbers are the Mac mini's. The display-link interval is an
Instruments-free proxy for frame pacing (a long main-thread layout stalls the next callback);
it does not see GPU time. The pane widths are the laid-out text view widths (three panes beside
a 360-point dock). Thirty selections and 474 frames are one run each, not the thirty runs
specs/01 asks for a budget claim.

shows the rebuilt text, with two panes plus a tab as specs/21 §7 wants. The chrome contrast

## 6. The cost to design around: the paragraph crosses the binding on every selection

`selectionToAnchors` takes the whole `Paragraph` by value: for the 1,000-verse set that is 1,000
`Segment` records with 27,000 `TokenSpan` records lowered from Swift to Rust on every selection
change, and the unit test's two core calls on that paragraph took 28–43 ms on the Mac and 35 ms
on the simulator, against 0.03–0.3 ms for a two-verse pane. In the measurement, the core calls
are 25–28 ms (p50) of the 69–78 ms (p50) selection latency; the rest is the text view's own selection, the
scroll-to-visible and the attribute paint. For a chapter (30–60 verses) the cost is well under a
millisecond; for a whole-book set or an "all verses in view" paragraph it is not, and it is paid
per selection *change*, so a drag pays it per handle move.

The surface does not need the whole paragraph: it needs the segments under the selection. The
measured alternative, within the existing API, is to hand the core a paragraph made of only the
segments the selection touches plus their offsets (the run map knows them), which is O(selected
segments); or, as a binding follow-up (not done here, names unchanged), a paragraph handle the
core keeps so the host passes an id and a range. Both leave the anchors identical because
`split_selection` is per segment. This is recorded in ADR 0001's findings as the one
measurement that changes a design, not a platform.

## 10. Decisions to review

1. **Verse markers live in the surface, not the core.** The core's `Paragraph` is the verses
   joined by one joiner; the display string carries the markers and the surface maps offsets
   (`RunMap`). ADR 0001 says the core returns render-ready runs with markers; until crates/text
   has that API (B062), the mapping is in Swift and JS, identically. Review: whether the run
   layout should come from the core now, so the three surfaces cannot drift on it.
2. **Painting uses storage attributes on Apple.** `NSTextLayoutManager.setRenderingAttributes`
   with `backgroundColor` was tried first and neither `UITextView` nor `NSTextView` drew it
   (the attribute was set; nothing was painted), so the highlight is a `backgroundColor` and
   `underlineStyle` attribute on the text storage, which both views draw. For the production
   reader with many highlights, a custom `NSTextLayoutFragment` drawing the ranges without
   touching the storage is the TextKit 2 way; not needed for the spike.
3. **Minted tokens for texts without a token layer** (KJV, N1904, the synthetic set) use the
   `edition:BBCCCVVVWWW` format with whitespace words, so the surface always has token ids to
   show; a real pack supplies the layer. The KJV, BSB Genesis and N1904 panes thereby claim ids
   no pack minted; they are labelled fixture on screen.
4. **A new conformance fixture** for Greek was added (section 1); it changes
   `conformanceFixturesJson()`'s content and the passed-case count every host prints. The Kotlin
   host was not run here (no Gradle run in this session); it iterates fixtures generically.
5. **The Selection view's word-tap prototype is gone**: the B004 "Selection and word study"
   view now preselects "one and only" through the surface (`selectPhrase`) and the study drawer
   quotes `workspace.selection`. B004's selection screenshots are superseded in look (native
   selection instead of tappable words); its other views are unchanged.
6. **Verse numbers in the Hebrew pane** sit at the reading start (the right edge) because the
   marker is a run inside the right-to-left paragraph, superscript, before the verse text; the
   first marker therefore hangs at the right end of the first line and the second at the right
   end of its line (`mac-anchors-1440-cross-verse.png`, `ipad-anchors-1024-cross-verse.png`).
   specs/21 §7 asks for exactly this; whether the number should instead sit in a margin column
   (as print editions do) is a design review for B062.
7. **The "17" marker is not painted** when a selection crosses the verse boundary, though the
   platform selection itself covers it: the highlight comes back from the core per segment, and
   the marker and the joiner belong to no segment. The picture reads as two highlighted runs
   with a bare number between. Alternatives for review: paint the joiner and marker when both
   neighbours are painted (a surface-side rule), or leave the gap so a highlight always shows
   exactly what is anchored.
8. **Unfree Firefox from nixpkgs** was downloaded into the gitignored `artifacts/` to run the
   Firefox half of acceptance 2 (`NIXPKGS_ALLOW_UNFREE=1`, `--impure`); nothing in the flake or
   the dev shells was changed to allow unfree packages. Review: whether the web shell should
   carry `firefox-bin` and `geckodriver` for `just test-dom-reader --browser firefox`, which means
   an unfree exception in `flake.nix`.
