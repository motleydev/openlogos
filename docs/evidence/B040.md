## How the contracts were decided

**Pane ids.** specs/12 and specs/03 ask for stable pane ids and independent history but do not
say what makes an id stable. The rule written down: an id is minted by the host when the pane
is created and never again; it is not the position (panes reorder, close and reopen), not the
resource (two panes may show one edition, a pane may change edition), and never reused in a
workspace, because B062's rule 2 makes a stored profile ignore ids the workspace no longer
has, which a reused id would silently adopt. The core can check shape, uniqueness and that an
id is not the pane's content id (`check_pane_identity`); it cannot check how a host minted an
id, so the rule is stated in specs/12 and a host that mints UUID- or ULID-shaped ids satisfies
it. The schema was not changed; the example ids `p1`..`p5` remain valid opaque tokens.

**Link groups and history.** A group is its label, membership is on the pane (B062's
"what is stored where"), a pinned pane is in no group, and a deliberate navigation's followers
are the other unpinned members. History is runtime state: specs/12 lists passage and scroll
anchor, not history, as persistent, so no 1.2 bump was made for it. Loop suppression is by
`(transaction id, pane id)`: a follower landing under the driver's transaction records a
programmatic visit and never propagates; the same transaction reported again in that pane is
a no-op.

**Migration.** One registry of pure steps, each `fn(Value) -> Result<Value>`, walked in order;
`migrate_workspace(value, "1.1", "1.1")` is the identity, so migrating twice equals once;
backwards, unknown and mismatched versions are refused. The 1.0 → 1.1 step sets
`schema_version` and an empty `layout_profiles`, which is exactly what B062's reader does with
a 1.0 file (every class derived from the pane order), and invents no scroll anchor. The fixture
checks the migrated document byte for byte, re-migration, the backwards refusal, untouched
pane ids and panes, and the same derived layout before and after at 1440, 1024 (standard and
accessibility), 390 and 3440 points. The validator cross-checks the fixture's input at 1.0 and
its expected document at 1.1 against the schema and against the archived example.

**Authority machine.** The states are the five the brief names. The fields are specs/03's
list plus `app_sha256` (the body the app's store holds), which a three-way comparison needs
to name both bodies of a conflict, and `operations` (ids issued, with the hash written and
whether the watcher has echoed them). The rules enforced by `apply`: a write carries the
writer's last-seen hash and is rejected into `conflict` when it differs from the binding's,
keeping the attempted body and the vault body by hash (the note store keeps bodies as sibling
revisions, specs/03 "Notes and synchronization"); under vault authority the app copy follows
the file (`reindex`) and `app_saved` is refused; under app authority an outside edit of the
published copy becomes a conflict rather than an import, because specs/13 says the bridge is
not a second sync engine; a migration holds a preview hash and a backup id, commits only the
previewed body, moves authority on commit, and migrating back to the app leaves the vault file
in place (never silently delete); a file that disappears detaches a vault-owned note, which is
read-only until relinked (reappearance, or `relink` by hand, possibly with a new vault id) or
converted to app-owned; a rename updates the path and nothing else. Idempotency: every
event with an operation id is checked against the issued operations first, in every state,
so a replay after a crash is a `duplicate` no-op even though the state has moved on; the same
id with another body is `operation_reused`. Echo suppression: an observation tagged with one
of our ids and carrying the hash we wrote is `suppressed_echo`; tagged with our id but another
hash, it is treated as an external change (and the echo is no longer awaited).

**Credentials.** The check is by the words of a key (`api_key`, `vault_password`,
`client_secret`, `access_token`, `credentials`, `private_key`, `bearer`, `cookie`, `oauth`,
`jwt`…) and by the shape of a string value (PEM private-key block, `Bearer ` header, common
provider prefixes such as `sk-`, `ghp_`, `xoxb-`, `AKIA` at plausible lengths). `token` is
allowed only as the token-id fields the anchor and alignment records use (`tokens`,
`token_ids`, `token_count`); `authority`, `author`, `key`, `secretary` and `passage` are not
flagged. It runs in Rust (`openlogos_notes::credentials`, tested over the four portable
record kinds' examples and over the serialized `NoteBinding` with every optional field set)
and in the validator over the same documents, over every note-authority fixture step and
over the property names the four schemas define. The schemas' `additionalProperties: false`
rejects an unknown key before the check does; the check names the reason and catches
credential-shaped values under innocent keys, which a schema cannot.

## Decisions to review

1. **`app_sha256` and `operations` on the binding.** Two fields beyond specs/03's list. The
   first is what lets a conflict name the app body and lets a detached relink tell "moved"
   from "edited"; the second is what makes replays no-ops and echoes recognisable without
   ignoring future file events. Both are portable, hash- and id-valued, and carry no text.
2. **An outside edit of an app-owned note's published copy is a conflict**, not an import and
   not ignored. The alternative (adopt the vault edit when the app body has not changed since
   publish) is a one-way sync the brief and specs/13 steer away from; a reviewer may prefer it
   as a `choose_vault` default in the UI, which the machine already supports.
3. **Deleting a vault-owned note's file ends in `app_owned`** with the app copy as the
   recoverable body; tombstoning the note itself is the note store's business (specs/12
   recoverable deletion). A dedicated `deleted` state was not added.
4. **`app_saved` is refused under vault authority and while detached.** Edits of a
   vault-owned note go through `write_to_vault` (write-through), so no stale app cache can
   overwrite a newer file; a detached note is read-only so a relink cannot lose an edit. A
   reviewer may want a local draft state here.
5. **Migrating back to the app leaves the vault file** as the published copy (nothing is
   deleted) and records the commit as an `adopt` operation so it replays as a duplicate.
   Cancelling a migration to a vault keeps the vault id and path the reader chose (the
   binding then looks like an app-owned note bound but not yet published).
6. **`convert_detached_to_app` needs no preview or backup**, since there is no vault body to
   preview; it adopts the app copy. Everything else that changes authority goes through
   `begin_migration` / `commit_migration`.
7. **Navigation history is not persisted** and the workspace schema stays at 1.1. If a
   later task wants history in the file, that is the 1.2 step the migration module's doc
   describes.
8. **Pane id minting is the host's**; the core checks shape and invariants only. A `p<n>`
   counter in the document was not added because it would need a schema field for the
   high-water mark; UUID/ULID ids satisfy the rule without one.
9. **Credential word lists** are deliberately narrow (`authority`, `author`, `key` alone and
   `passage` pass; `token` is allowed only for token ids and counts). A future field named
   `*_token` for a provider handle would be rejected until it is allow-listed, which is the
   intended friction.
10. **Shared files touched:** `justfile` and `flake.nix` (wasm check lists gain
    `openlogos-notes`), `tools/validate.py`, `crates/conformance/src/lib.rs` and
    `Cargo.toml`, `crates/workspaces/src/lib.rs` (module declarations and re-exports; B062's
    code is unchanged), `crates/README.md`, `examples/README.md`, `tools/README.md`,
    `VALIDATION.md`, `apps/apple/README.md`, `apps/android/README.md`,
    `specs/03-data-model.md` (one clause), `Cargo.lock`.
