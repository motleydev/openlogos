## Source and rights

`rights/S09.json` is `approved` (steward, 2026-11-08), CC BY 4.0, with `local_read`, `public_index`
and `redistribute` allowed. The importer runs the B071 gate (`crates/preview-pack/src/rights.rs`)
unchanged. It checks the status and permissions. It checks that `MANIFEST.sha256` hashes to the
record's `artifact_sha256` and equals `rights/S09/manifest.sha256`. Both listed files must hash as
listed: `cross-references.zip` `045f1c5d…` and `cross-references-page.html` `6674984c…`. The parser
reads the zip bytes that were hashed. The data file inside, `cross_references.txt`, is 8,303,003
bytes with SHA-256 `203e2bc2ae11de5c9745c86504fe3e32c841ac8a59a6453dc68d34614f69769a`. Its header is
`From Verse⇥To Verse⇥Votes⇥#www.openbible.info CC-BY 2026-10-26`, which matches the record's
`release`.

**Attribution.** CC BY 4.0 §3(a) asks for the creator, a licence notice with its URI, a disclaimer
notice and an indication of changes. The page names no person and carries no copyright line for the
data. The pack's `attribution`, which every list item carries, is the rights record's sentence plus
the licence URI, the changes made, and the as-is notice:

> Cross references from OpenBible.info (https://www.openbible.info/labs/cross-references/), CC BY 4.0; primarily derived from the public-domain Treasury of Scripture Knowledge, with votes seeded from the Topical Bible and Twitter Bible Search. Licence: https://creativecommons.org/licenses/by/4.0/. Changes: rows converted into an OpenLogos relation pack; references, ranges and votes as published; shown in each edition's verse numbering. Provided as is, without warranties.

The page's ESV notice covers the verses the website displays. None of them are in the data file.

## Decisions

Each one is a line of code a reviewer can change.

1. **One typed edge per published line**, in the B064 pack schema, which the link index installs
   like any other pack (tested). `src_work = dst_work = "bible"`, and the locators are `BBCCCVVV`
   verse ids in the pack's scheme. A range target is written `first-last`, as in specs/19. `weight`
   is the published vote count. `provenance_kind` is `curated`, `review_state` is `source_attested`,
   `source_work` is `S09` and `method` is `S09:votes`. **The edge's id is the line of the file**,
   so each row carries its own source locator; the second reader checks all 344,799. The pack
   stores these rows in the coded edge storage (decision 13); readers see them through the `edge`
   view exactly as above.
2. **The relation kind is `unspecified`.** OpenBible does not say whether a link is a quotation,
   an allusion or a theme, so none is claimed (specs/17).
3. **Direction.** Rows run as published. A reverse lookup (`include_reverse`) turns round the rows
   listed under *other* verses that point at the passage, and labels them `reverse_derived`. A
   single-verse target is found through the destination postings. Each of the 88,150 range
   targets is also kept in `xref_range` as its chapter segments (88,834 rows), so a verse inside
   a range finds the link: `first BETWEEN v − 999 AND v AND last ≥ v`.
4. **Votes are kept as published.** Zero and negative counts are not dropped, clamped or rescaled,
   and there is no relevance model. Lists put published items first, ordered by their best vote,
   then derived items the same way, then the canonical order of the target. Zero and negative rows
   therefore come last. Their meaning goes in the manifest in the source's words (`xref_votes_meaning`):
   a popularity signal, not accuracy, relevance or textual dependence.
5. **Scheme.** I checked the scheme against the data and found `eng`. Every one of the 777,748
   references (each source, each single target, both ends of each range) is an `eng` verse, and the
   build stops on any that is not. 3,384 of them are verses `org` does not have: Joel 3 (500),
   Mal 4 (420), Num 16 (292), 1 Kgs 4 (275), Dan 4 (257), Joel 2 (239), and others. That rules out
   `org`. The file also uses 3 John 1:15 (5 times), a verse `eng` has.
6. **Mapping happens at read time**, into the edition asked about, with the canon table (S51). One
   pack serves every edition. The importer counts the same rules over every row (below). A range
   maps by its two ends and stays a range.
7. **Nothing is dropped.** Each item has a `mapping` (exact, partial, ambiguous, unmapped) and an
   `availability` (printed, partly printed, not printed, book not in edition, unmapped).
   - An item the edition cannot show has no preview. Its `available_in` lists the installed editions
     that print it. No other translation's text is shown in its place.
   - When a range end has no counterpart, the range keeps the part that maps and is marked
     `partial`. For example, `eng` Acts 19:41 has no `org` verse, so Acts 19:23–41 becomes
     Acts 19:23–40 in the SBLGNT.
   - A single verse with no counterpart stays `unmapped` under its published label.
8. **Deduplication.** Items with the same visible target merge into one. Every assertion stays, with
   its source verse, its target as published, its votes, its line and its direction. Equal targets
   come from different verses of a passage, from a published link plus its reverse, or from two
   `eng` verses that land on one `org` verse.
9. **Every verse of the passage is looked up, printed or not.** A verse the edition omits still has
   the links the source lists under it.
10. **Pages.** `offset` and `limit` page the list. Preview text (the edition's first
    `preview_verses` verses of the target, joined by a space) is read only for the page returned,
    because reading a chapter chunk is nearly all the cost.
11. **Enablement.** `nav.cross_references` was already registered (B077). It stays disabled with
    "Needs cross-reference data" until the host calls `set_data_layers(["cross_references"])`.
    After that it needs only a passage. The command is host-performed. An item opens with
    `tab.open_edition` (`resource_id`, the item's `target`). A test shows that this leaves the main
    tab's passage and focus where they were.
12. **Output** goes to `<out>/relations/`. `just preview-pack` now carries `relations/` over when it
    replaces the output, so a text rebuild does not delete the cross references.
13. **Coded edge storage** (`crates/retrieval-sqlite/src/pack/coded.rs`, the lead's plan A). It is
    opt-in through `PackBuilder::create_coded_edges`, and the manifest says `edge_storage = coded-1`.
    Every other pack keeps the default layout. What changed in the schema of a coded pack:
    - The `edge` table and its `edge_src` / `edge_dst` indexes are gone.
    - `edge_term(kind, id, value)` is a dictionary per column kind (`work`, `rel`, `method`,
      `provenance`, `review`). Ids start at 0 in first-seen order, so the usual values cost no
      payload bytes.
    - `edge_row(id INTEGER PRIMARY KEY, …)` has the `edge` columns, with codes in place of text.
      A locator that is a plain decimal number is stored as an integer, anything else as text.
      `id` is the writer's choice (here the line). It is an `INTEGER PRIMARY KEY` because a plain
      `rowid` did not survive `VACUUM` in a test.
    - `edge_posting(side, work, locator, rel, rowids)` holds roaring bitmaps of ids per source
      (`side` 0) and per destination (`side` 1), in place of the two B-tree indexes.
    - `edge` is now a view with exactly the old columns, value types and text, so the link index
      installs a coded pack with unchanged SQL.

    `links.rs`, its tests, `PACK_SCHEMA_VERSION` (`b068-1`) and every other reader are unchanged.
    New tests show that the view returns the same values and types as the default table, and that
    the link index gets identical `link`, `work`, `rel` and `cited_count` rows from either layout.

Reading:

- **The budget is met** for a verse's first page natively (p95 7.3 ms, 6.4 ms and 4.1 ms) and in
  wasm (0.8 ms).
- The **whole list** of published links is also under budget natively (p95 8.0 ms).
- It is **missed only for the whole list with reverse links in the BSB** (p95 18.5 ms). Paging
  brings that case to 9.1 ms.
- The data lookup, mapping and merging cost 0.5 ms p95. Natively, the rest is preview text:
  `FilePack` reads, hashes and parses a chapter chunk from disk on every call. In a browser, supplied
  chunks are held parsed, which is why wasm is faster. A small parsed-chapter cache in the native
  library would close the gap. It is not built.
