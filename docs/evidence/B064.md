## Deviations from a naive reading of the spec

Two engine decisions that a reader of specs/19 would not expect, both forced by the data and
both covered by tests and by the oracle comparison:

1. **Feature values compare in NFC.** N1904's lemma strings (and MACULA's) carry the Greek
   Extended oxia code points (`θεός` is `03B8 03B5 1F79 03C2`), while a query typed on a
   modern keyboard produces the tonos forms (`03CC`). Before the fix 7 of the 10 lemma queries
   returned 0. The pack builder stores dictionary values as NFC and the engine folds the query
   value the same way (`tokenizer::feature_key`); display text is still never normalized
   (specs/03). The oracle applies the same NFC fold on both sides so that it compares meaning,
   not bytes.
2. **Discontinuous containers keep exact slot membership.** 18,797 of N1904's 226,392
   ingested containers (sentence, clause, phrase, wg) are discontinuous. The first design
   stored each container as its hull span (first..last token); the oracle then disagreed on
   five queries (PEER, XPEER and clause/phrase scopes: for example q29 4168 vs 4175). The
   builder now takes the exact slot list for such containers and derives the per-token
   innermost map from it; the `container` row keeps the hull span, which `ANCESTOR` still
   tests (the two ANCESTOR queries matched either way). After the change all fifty queries
   match.

Also worth a reviewer's eye: `Before { distance: Some(n) }` means `0 < pos(b) − pos(a) ≤ n`
(adjacent is 1), `Within` is symmetric, slots always bind distinct tokens and counts are
ordered tuples (the same lemma in two slots counts each pair twice, as Text-Fabric does).

### wasm32 decision

Two hours were allowed. Option (a), SQLite compiled into the Rust module, was taken and
works; option (b), the official `@sqlite.org/sqlite-wasm` JS build driven through
wasm-bindgen, was not built and is the recorded fallback.

- rusqlite 0.41 has its own wasm backend (`ffi-sqlite-wasm-rs`), so the engine's code is
  identical on native and wasm32; only `Cargo.toml` gates the dependencies. sqlite-wasm-rs
  compiles the amalgamation with FTS5 (also RTREE, session, math functions) behind a musl
  shim and exposes the full C API, including `fts5_api` and `sqlite3_bind_pointer`, so the
  tokenizer registration is the same code.
- Verified in headless Chrome 156, in a dedicated worker (`crates/ffi/tests/worker.rs`,
  `scripts/wasm-test.sh --features retrieval`): `sqlite 3.53.0 fts5 greek_hits 1
  hebrew_hits 1 mode ol-norm-1`; `test result: ok. 6 passed; 0 failed`.
- Version pins: sqlite-wasm-rs **0.5.5** (wasm-bindgen ^0.2.104, compatible with the
  0.2.121 CLI the flake pins); 0.6.2 requires wasm-bindgen ^0.2.128 and would need the flake's
  CLI bumped. 0.5.5 bundles **SQLite 3.53.0** and 0.6.2 bundles 3.53.4; specs/19 asks for
  3.54 or later for the OPFS locking fix. sqlite-wasm-rs accepts a custom source directory
  (`SQLITE_WASM_RS_SOURCE_DIR`, with its `bindgen` feature), which is the way to get 3.54
  before upstream moves.
- **Not done on wasm:** sqlite-vec (its C file includes libc headers the wasm32 target has
  no sysroot for; compiling it against the same musl shim is the next step), and the OPFS
  `sahpool` VFS (`sqlite-wasm-vfs` 0.2, wasm-bindgen ^0.2.104) — see R7.
- Toolchain finding: the Nix clang wrapper adds `-fzero-call-used-regs=used-gpr`, which
  the wasm32 target rejects, and Xcode's clang has no wasm32 back end. The dev shells now
  export `CC_wasm32_unknown_unknown` pointing at the unwrapped Nix clang 21.1.8 (same store
  path as the wrapper's inner compiler, so no new download). The sandboxed `nix flake check`
  wasm derivation does not have this wiring yet and keeps the old crate list, with a comment.

## R9 — relations on about 5M edges across 200 packs

`openlogos-retrieval-bench r9 <dir> --runs 50` generates 200 pack-shaped sources: one
OpenBible-scale cross-reference pack (340,000 `cross_reference` edges verse → verse with
vote weights, curated), 20 lexicons (lexeme → verse `attested_in`, lexeme → lexeme
`synonym_of`/`cognate_of`), 19 other works (section → verse `cites`, plus `quotes` chains
between works, extracted) and 160 commentaries (paragraph → verse `cites`) of varying size;
4,999,930 edges in all. Destinations follow a power law with exponent 0.5 over 29,725 verses
(busiest verse ≈ 0.6 % of all citations, 27,894; a first run with exponent 1 put 323,212 on
one verse, which no real library does, and is reported only as the "steep skew" column).
Pack files: 825,487,360 bytes, generated in 167 s. The link index is built from 199 packs,
then the last commentary is installed, removed and reinstalled incrementally.

Steep-skew control (first run, exponent 1, one verse with 323,212 inbound edges): backlinks (limit 100) on popular verses p50 6.7 ms / p95 693 ms, backlink_count p95 7.8 ms, most_cited 525 ms. The cost of `backlinks` on a hub is the `ORDER BY weight DESC` sort over every inbound row; with a relation filter (`rel=cross_reference`, p95 0.8 ms) or without the sort it is index-bound.

An intermediate version of the batched traversal joined the temp frontier table without pinning the join order and the planner scanned all 5M `link` rows per hop (depth 1: 1.3 s p50). `CROSS JOIN` plus a primary key on the frontier table restored 0.9 ms; this is the kind of plan regression the conformance suite should guard with a timing assertion.

**Against the targets.** specs/19 names no numeric R9 targets yet; measured against specs/01's budgets (reference jump ≤ 100 ms, search ≤ 300 ms): backlinks and backlink counts are inside 100 ms at p95 even on hubs; 1–2 hop neighbourhoods are inside 25 ms; capped 3–6 hop traversals that materialize 5,000 nodes with their paths sit at 100–140 ms p50 and 310–360 ms p95 (a UI cap of 500 nodes would be an order of magnitude less); quotation chains across works (depth 6, fan-out 50, 644 nodes) 14 ms p50 / 64 ms p95; the recursive CTE without caps is fast to depth 3 (1,322 nodes in 3.6 ms) and is the right tool for counts. The library-wide aggregate `most_cited` (0.4–1.9 s) is the one miss and is a design fix, not an engine limit: maintain a per-destination count table on pack install. **No graph-engine escalation (GraphQLite, LadybugDB) is warranted by these numbers.**

Simulator: **not run** for R9 (the iPad simulator costs 2.7 GB of disk to boot and the
lead asked for Mac numbers only). Physical devices: none.

## Decisions to review

- `openlogos-retrieval` now has serde and thiserror dependencies (both wasm-clean) so the
  query AST serializes for the bindings.
- Feature values compare in NFC; display text does not (above).
- `ANCESTOR` tests hull spans while `PEER`/`XPEER`/scopes use exact membership; a container
  with a gap can therefore "contain" a token in its gap for `ANCESTOR` only. Storing exact
  runs per container would close this.
- sqlite-vec is the only C package compiled for speed (`-O3`, NEON); SQLite itself stays at
  opt-level z. Measured gain below (R5 baseline).
- The `retrieval` feature of crates/ffi is off by default, so the generated Swift/Kotlin/TS
  bindings are unchanged; `retrieval_smoke` and `retrievalProbe` are probes, not the API.
- The link index stores integer work and relation ids with text locators; at 5M edges it is
  489 MB (98 bytes per edge). Integer verse locators and `WITHOUT ROWID` would roughly
  halve it. `most_cited` (a library-wide aggregate) should be a summary table maintained on
  pack install, not a per-query `GROUP BY` over millions of rows.
- The test fixtures live inside the crate's test modules rather than under `fixtures/`; the
  SBLGNT excerpt is three verses with provenance in the module doc.
- `ingest.rs` is a spike-grade Text-Fabric reader, not the pipeline of specs/19; it exists so
  the engine and the oracle see identical data.
